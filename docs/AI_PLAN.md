# AI 融合方案

更新日期：2026-10-30。

实现状态（2026-10-30 下午）：A“环境与选卡规划”已实现（`src/env-plan.mjs`、`/api/plan`、页面“AI 环境与选卡”）；B 并入 A（源实例 `get_arch_list()` 输出可直接贴入检查目标卡）；C 只实现“拿到实例后的检查命令”，报错诊断沿用原诊断模式；D 未做。模型使用用户自己的 API Key（DeepSeek、百炼或其他兼容接口）。开发期间曾提供本机 Ollama 选项并用 qwen3:4b 评测；2026-10-30 用户决定去掉（不是每位用户都装有 Ollama）。评测见 `eval/PLAN_EVAL.md`。

一个任务仍只等一种型号（第 3 节 A 末尾提到的“一个任务接受多个型号”没有做，需要单独评审）。

## 1. 前提

- 用户没有 GPU，正是为了抢 GPU 才用这个工具。AI 只用远程 API（DeepSeek、百炼等，用户自己的 Key，算力在服务商）。不在 AutoDL 上部署模型，不要求本机 GPU。
- AI 不进入扫描和点击的循环：扫描 1 秒一轮，模型调用要几秒到几十秒、要花钱、结果不稳定，放进去只会更慢、更不可靠。
- AI 只做规则做不好的事：读懂非结构化的项目资料与报错。凡是能用确定性规则做的（解析 requirements.txt、版本比较、架构规则、目录匹配），都用规则做。
- 没有 Key 时，核心功能照常；新功能中规则那一半也照常可用。

## 2. 现有“AI 环境助手”的评价

做得对的地方：默认关闭；用户自己的 Key；只发送用户提交的文本；输出固定 JSON；引用必须出现在输入原文中；不执行任何操作；不改任务的硬约束。

主要问题：它是一个独立的分析页，与抢卡流程没有连接。它不知道 AutoDL 当前有哪些官方镜像、各地区有哪些型号和空闲数、源实例是什么环境；输出是文字建议，用户还要自己把建议翻译成表单。这样的 AI 只是套了一层通用模型接口，没有形成实质改进。

建议：保留它的安全设计，把功能改成第 3 节的“环境与选卡规划”，结果直接成为可确认的任务草稿。

## 3. 方案（按优先级）

### A. 环境与选卡规划（核心）

用户粘贴或选择 requirements.txt、environment.yml、README、Dockerfile 片段或报错日志，得到：

1. 硬约束：框架与版本范围、Python 范围、所需 CUDA 下限、显存需求、单卡或多卡。每条附出处（原文片段）和来源类型（规则解析 / 模型推断）。
2. 官方镜像：从已同步的 AutoDL 官方镜像目录中选出满足约束的完整四级路径。
3. 可接受的 GPU 型号：按已同步的各地区型号目录，排除架构不符的（如 Blackwell 需 CUDA ≥ 12.8）、显存不够的，列出各地区当时的空闲/总数。
4. 一份任务草稿（型号、卡数、地区、镜像），用户确认后填入表单；规则继续做所有提交前核验。

分工：
- 规则解析器：requirements.txt、版本锁定、`torch==x+cu121` 这类明确写法。没有 Key 也能用。
- 模型：只从 README、报错等自然语言中抽取规则读不出的约束（例如“训练需要 24GB 以上显存”），必须给出原文片段，程序核对片段确实存在；不允许输出目录里没有的镜像或型号。
- 求解器（确定性）：把约束与真实目录求交集并排序。

为什么对抢不到卡的人有用：很多项目其实不必非要某一张卡。把“只等 4090”扩展成“24GB 以上、驱动支持 CUDA 12.1 的这几种型号”，可等待的目标变多，抢到的概率更高。这需要让一个任务接受多个型号（按顺序或按价格），是任务模型的改动，应单独评审。

### B. 克隆换型号前的兼容检查

克隆时源环境原样复制。用户把源实例里 `pip list`、`nvcc --version`、`python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.get_arch_list())"` 的输出贴进来：规则判断目标型号的计算能力是否在 `get_arch_list()` 中；模型解释看不懂的部分。比现在只按镜像 CUDA 判断更准，能在付费前发现“PyTorch 不支持 5090”这类问题。

### C. 拿到 GPU 之后的验证与报错诊断

按任务的真实配置（型号、镜像、CUDA、是否复制数据盘）生成一组只读核验命令和最小测试步骤，用户自己在实例里运行。运行报错再贴回来，现有诊断模式结合这些事实给建议。不自动执行任何命令。

### D. 不认识的平台提示（离线、低优先级）

点击后出现程序不认识的提示时，提示原文已写进日志。可以让模型把这些原文归类（竞争失败 / 主机问题 / 账户问题 / 需要人工），只作为维护者补充识别规则的建议，不在运行中改变判断。

## 4. 不建议做的

- 让模型决定是否点击、点哪台主机。
- 用模型“预测”何时有卡：没有可靠数据支撑；如要做，先用确定性统计（各地区、各型号在一天中何时出现空闲）。
- 在远程 GPU 上部署模型，或要求本机有 GPU。
- 只加一个聊天窗口。

## 5. 如何证明 AI 确有作用

准备约 30 个真实开源项目（含 README 与依赖文件），人工标注正确的约束与可用镜像、可用型号。比较三组：只用规则、规则 + 模型、人工。报告约束抽取正确率、建议了不可用镜像或型号的比例（应为 0，由求解器保证）、遗漏率和每个项目的处理耗时，并列出失败案例。效果不好的部分缩小范围，不夸大。

## 7. 参考项目

- CrazyAutoDL（A2ureeE，Swift/Electron 桌面应用，2026-10-30 查看 README）：调用 AutoDL 网页端接口（README 自述“并非官方公开 API”），监控指定实例所在主机，有空闲卡就把原实例开机；另有余额、账单看板、内嵌登录捕获 Token。仓库根目录没有 LICENSE 文件，不能复制其代码。它只对已有的原实例有效，适用范围窄；按用户 2026-10-30 的决定，本项目暂不参考这种模式，也不做“原实例开机优先”。
- 本项目的差异：只用可见页面 DOM，不调用私有接口；新建与同地区克隆（含跨型号、复制数据盘）；点击前持久化提交边界、点击后对账，不重复付费；被拒绝的主机暂时不选。
