# 环境与选卡规划评测

日期：2026-10-30。评测脚本 `scripts/eval-plan.mjs`，用例 `eval/plan-cases.mjs`，原始结果 `eval/plan-results-*.json`。

## 要回答的问题

规则能不能单独完成“从项目资料读出运行条件”？加上本机开源小模型后，读对的有多少、读错的有多少，对“哪些 GPU 型号能用”的结论有什么影响？

## 方法

- 用例：12 个公开 GitHub 项目（nanoGPT、ChatGLM3-6B、Qwen-7B、stable-diffusion、ControlNet、LLaVA、whisper、FastChat、yolov5、segment-anything、ChatGLM-6B、LLaMA-Factory）各配一句用户需求，外加 1 个合成的提示注入用例。资料从 GitHub 现取（`HEAD`），按“用户只粘贴相关段落”截取；结果中记录每个文件的 SHA-256 前 16 位与读取时间，资料不随本仓库分发。
- 标注：只标资料原文明确写出的 PyTorch、Python、CUDA 版本条件与单卡显存，每条写明原文依据（见 `plan-cases.mjs` 的 `basis`）；没写的标“无”。显存取与用户需求对应的那个数字。标注由开发者完成，未经第二人复核。
- 比较两组：A 只用规则；B 规则 + 本机 Ollama `qwen3:4b`（Q4_K_M，digest 359d7dd4bcda，Ollama 0.40.5，CPU 推理，`temperature 0`，每个用例 1 次）。B 中模型输出须通过引用核对，依赖版本以规则为准。（这是开发期间的设置；产品现已改为只接用户自己的 API Key，见“结论与限制”最后一条。）
- 字段评分：版本条件在一组候选版本上比较“允许的版本集合”，相同为正确，更窄为偏严，其余为错误；显存相差 ≤ 0.5GB 为正确。“漏读”= 标注有值但没读出；“多读”= 标注没有但读出了值。
- 判定层：用 AutoDL 创建页实际出现的 17 个型号名，分别按标注与按读出的条件求解（17 × 13 = 221 个判断）。“误放行”= 按标注为不满足或需核对、按读出却给出可用/有风险；“该放行未放行”= 按标注可用/有风险、按读出却为不满足或需核对。标注没写显存的用例，按标注的判断也是“需核对”。不比较特性（标注不含特性）。下面的判定层数字都按修正后的判定规则（见“判定规则的修正”）用保存的模型输出重新评分。

### 引用核对的作用

第 1 轮模型共输出 13 条显存候选，其中 7 条通过核对、6 条被丢弃。被丢弃的 6 条中，3 条是编造的数字（nanoGPT、yolov5、segment-anything），1 条选错了行（LLaMA-Factory），2 条数值正确但引用不是连续原文（Qwen、whisper）。没有核对时，这 4 条错误会直接进入选卡结论；代价是丢掉 2 条正确值。

## 第 2 轮（提示词调整后，同一评测集）

根据第 1 轮的失败（表格引用拼接），在提示词中加了一句通用要求：“表格只复制含该值的那一行，不要把表头和数据行拼在一起，也不要用省略号连接多处”。这是看过评测结果后做的调整，第 2 轮与第 1 轮用同一评测集，**存在针对评测集调整的偏差**，不能当作独立测试结果。

| 指标 | A 只用规则 | B 第 1 轮 | B 第 2 轮 |
| --- | --- | --- | --- |
| 版本字段（18 个有标注 / 21 个无标注） | 18 正确 / 0 多读 | 18 正确 / 0 多读 | 18 正确 / 0 多读 |
| 单卡显存（9 个有标注） | 2 正确 | 6 正确，3 漏读 | **7 正确**，1 漏读，1 读错 |
| 显存在“资料没写”的 4 个用例中多读 | 0 | 1 | 1（ControlNet，同第 1 轮） |
| 判定层误放行 | 7 | 16 | 19（其中 17 个为“有风险”） |
| 判定层该放行未放行 | 16 | 16 | 0 |
| 模型耗时中位数 | — | 26 秒 | 23 秒（14～30 秒） |

第 2 轮的变化：

- whisper 的引用改为只复制 large 那一行，通过核对，读对 10GB。
- Qwen-7B 的引用仍把表头与数据行拼在一起，被丢弃（漏读）。
- LLaMA-Factory-14B 这次只复制了一行，引用通过核对，但选的是“QLoRA 2 比特”行的 70B 一列（24GB），应为“LoRA 16 比特”行的 14B 一列（32GB）。**引用核对只能证明原文存在，不能证明模型读对了行和列**；3 张 24GB 的卡因此被判为“有风险”而不是“不满足”。
- 其余用例与第 1 轮相同。合成注入用例中模型仍输出 24（原文值）；规则仍把注入文字中的“4GB”列为候选。

现在代码中的提示词是第 2 轮版本。

## 判定规则的修正（2026-10-30 傍晚）

用户反馈：只写“部署27b模型”时，RTX 3080 Ti、GTX 1080 Ti 等显存不够的卡都显示“可用”。原因：资料没写显存时，旧规则不检查显存，型号显示“满足已读出的条件”。修正：

1. **显存要求未知时不判“可用”**，判为“需核对”，并提示写明模型大小。
2. **资料没写显存时按模型大小估算**（确定性公式，不用模型）：推理按 EleutherAI《Transformer Math 101》的经验式，总显存 ≈ 1.2 × 参数量 × 每参数字节（FP16/BF16 为 2，INT8 为 1，INT4 为 0.5），27B 推理约 65GB；微调按 LLaMA-Factory README“硬件依赖”估算表，参数量不在表中时按最近一列等比换算；多卡按卡数平分。资料写明的显存优先于估算。
3. **资料中有多个显存数字时，按最大的判断**（保守），并提示写明要跑哪个模型。
4. **显存要求来自模型补充时**，满足的型号标为“有风险”并给出原文，不标“可用”。

估算规则是看过本评测集之后写的；LLaMA-Factory-14B 用例的标注本身来自同一张估算表，估算与之一致不能算独立验证。Qwen-7B 用例中，估算（QLoRA 4 比特约 6GB）低于 Qwen README 的实测值（11.5GB），2 张 11GB 的卡因此被误放行：估算表是经验值，不含长序列与大批量，结论页已注明“实际以实测为准”。

字段层的数字（读对几个显存）不受判定规则影响；判定层用 `node scripts/eval-plan.mjs --rescore plan-results-run1.json --out plan-results-run1.json`（第 2 轮同理）按保存的模型输出重新评分，不再调用模型。

## 结论与限制

- 依赖文件和安装说明里的版本条件，规则已能读准（18/18，0 多读），这部分不需要模型。
- 单卡显存经常写在表格或按模型大小、用途分列的说明里，需要结合用户的需求挑选。这正是规则做不好、模型能补上的部分：读对的显存从 2 提高到 6（第 1 轮）、7（第 2 轮，提示词针对评测集调整过）。
- 判定层：只用规则时偏保守，误放行 7 个，另有 16 个能用的型号停在“需核对”；加上模型（第 2 轮）后，这 16 个都给出了结论，但两次读错（ControlNet 的可选模式、LLaMA-Factory 的表格列）使 17 个型号被判为“有风险”，误放行合计 19 个。模型补充的条件因此一律标为“有风险”并显示原文，由用户核对。
- 4B 小模型会编造数字、选错行、把可选模式当作要求。引用核对挡住了编造的数字与拼接的引用，但挡不住“引用真实但理解错”（ControlNet、第 2 轮的 LLaMA-Factory）和资料中夹带的注入文字。所以模型补充的条件在页面上单独标注并显示原文，结论须由用户确认。
- 样本小（12 + 1），标注者即开发者，模型每例只跑 1 次；判定层只用型号名规格表，没有核对真实库存、价格与驱动；没有在真实 GPU 上运行项目来验证标注。结论只说明这一组数据上的差异，不能推广为准确率。
- **评测所用模型与产品不同。** 两轮的模型都是本机 Ollama 运行的 Qwen3-4B（4B 参数的开源小模型）。2026-10-30 起，产品改为只接用户自己的 API Key（DeepSeek、百炼等），不再提供 Ollama 选项。提示词、引用核对与合并规则没有变；请求方式从 Ollama 原生接口（JSON Schema 约束输出）改为 Chat Completions（DeepSeek 用 `json_object`）。用 API 模型在本评测集上的结果尚未测量，不能直接套用上面的数字。

## 复现

```powershell
node scripts/eval-plan.mjs --rules-only       # 只评测规则，不调用模型
$env:AI_EVAL_API_KEY = '你自己的 Key'          # 模型组：用自己的 API Key，按服务商计费
$env:AI_EVAL_PROVIDER = 'deepseek'            # 或 dashscope / custom；可选 AI_EVAL_MODEL、AI_EVAL_BASE_URL
node scripts/eval-plan.mjs --out plan-results-api.json
node scripts/eval-plan.mjs --only FastChat-13B,LLaVA --out plan-results-api.json
```

Key 只从环境变量读取，不写入结果文件。13 个用例的请求合计约 1.1 万 Token（第 2 轮实测）。第 1、2 轮的结果由当时代码中的本机 Ollama 接口生成，现在的脚本只能用 API 模型重测。

资料按 `HEAD` 读取，上游更新后内容可能变化；对照结果中的 SHA-256 判断是否为同一份资料。缓存在 `.cache/plan-eval/`，加 `--refetch` 重新读取。
